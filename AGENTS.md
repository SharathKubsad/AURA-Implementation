# AGENTS.md
Instructions for any AI coding agent (Claude Code, Cursor, Codex, Copilot Workspace, etc.) working in this repository. Read this file fully before touching code. The full build plan lives in `PROJECT_MANUAL.md` — read that too before starting any task.

## 1. What this project is
A hybrid machine-learning framework for detecting **fileless malware** from volatile memory and live behavioral telemetry. It has four objectives, built in order but engineered to run as one pipeline:

1. **Benchmark dataset** — merge public fileless-malware datasets with a custom dataset generated by executing known malware families in isolated sandboxes and extracting process, command, network, and memory features via memory forensics.
2. **Real-time hybrid detector** — four lightweight models (Process, Command, Network, Memory) score live telemetry independently; if any flags suspicion, a partial memory dump is pulled and scored; confidence scores are fused (simple average) against a 0.60 threshold for a Benign/Malware verdict.
3. **Multi-class extension** — when Objective 2 flags Malware, the same already-extracted features are fused into one vector and passed to a multi-class classifier to name the malware family.
4. **Assurance layer** — robustness testing (unseen variants of known families), generalization testing (unseen feature subsets), and explainability (SHAP + LIME) on top of the trained models.

Two people are building this together. Track ownership is defined below and in `PROJECT_MANUAL.md` §2. **An agent must not modify files owned by the other track without the human confirming it first.**

## 5. Coding standards

- Python 3.11+, type hints on every public function signature.
- Format/lint: `black` + `ruff` (line length 100). Run `ruff check . && black --check .` before any commit.
- Docstrings: Google style, one-line summary + Args/Returns.
- Tests: `pytest`. Every new module gets at least one smoke test in the mirrored `tests/` path.
- Commit convention: Conventional Commits — `feat:`, `fix:`, `data:`, `exp:` (experiment/training run), `docs:`.
- Branching: `main` is protected. Work in `track-a/<feature>` or `track-b/<feature>` branches. Every PR needs one review from the other track's owner before merging into `main`.
- Config, not hardcoding: thresholds (e.g. the 0.60 fusion threshold), file paths, and model paths live in `config/*.yaml`, never hardcoded in scripts.

## 6. Malware-handling rules (hard constraints, apply to every agent — human or AI)

- **Never paste live malware code, decoded payloads, shellcode, or exploit source into any file, notebook, commit message, PR description, or issue in this repo.** Reference samples only by filename + SHA-256 hash + source dataset in `sandbox/execution-logs/`.
- **All execution happens inside isolated, snapshotted, host-only-networked VMs** (see `PROJECT_MANUAL.md` §4.3). Nothing malicious ever runs on the host OS or a bridged/NAT network adapter.
- Any samples kept on disk for reference are stored as password-protected zip archives (conventional password: `infected`) **outside** the git repo, referenced by path only.
- `.gitignore` must always exclude: `*.raw`, `*.mem`, `*.vmem`, `*.dmp`, `*.lime`, `*.pcap`, `*.pcapng`, `data/raw/`, and any `*.zip` under `sandbox/`.
- If an agent is asked to "automate running the malware," it may only orchestrate already-named, publicly documented security tools already selected in `PROJECT_MANUAL.md` §4.3 (e.g., Metasploit, Empire, PowerSploit, Cobalt Strike trial). Agents do not author new payload/exploit code — that is out of scope for this repo and for this assistant.

## 7. Data & experiment versioning

- `data/processed/` and `models/*/artifacts/` are tracked with **DVC**, pointed at a remote the team agrees on (Drive/S3/etc. — fill in `.dvc/config` once chosen).
- Every training run logs to **MLflow**: hyperparameters, metrics (accuracy, precision, recall, F1, ROC-AUC, FPR, FNR), confusion matrix artifact, and — for tree models — a SHAP summary plot.

## 8. Key interface contracts

**Feature schema** (`forensics/schemas/*.py`, pydantic models) — one schema per category: `ProcessFeatures`, `CommandFeatures`, `NetworkFeatures`, `MemoryFeatures`. All four extraction pipelines (from dumps) and all four live collectors (from the running OS) must emit data conforming to these same schemas — this is what lets Objective 1's offline features and Objective 2's live features share one model per category.

**Detection API** (`framework/api/main.py`, FastAPI):
```
POST /v1/detect
  → runs process+command+network collectors, triggers memory model if needed,
    returns { verdict: "benign"|"malware", confidence: float,
              per_model: {process, command, network, memory}, family: str|null,
              family_confidence: float|null }
```
